## 一、当前架构概览

关卡系统由 **三条独立管道** 组成，服务于不同游戏模式：

```
关卡系统
├── 管道 A: 叙事关卡 (LevelPlugin + ZoneBank 硬编码)
│   ├── GameLevel 状态机（10 个关卡枚举）
│   ├── ZoneBank 硬编码区域配置（floor_size, glb_scene, floor_color）
│   ├── spawn_narrative_zone → 生成地面/GLB 场景
│   └── cleanup_level → 销毁 LevelEntity
│
├── 管道 B: LevelTool (RON 数据驱动)
│   ├── level_config.ron → LevelToolConfig
│   ├── spawn_level_content → 生成 NPC/收集品/ProximityModel/音效
│   └── 与管道 A 并行触发（同一 OnEnter 事件）
│
├── 管道 C: TD 关卡 (独立子系统)
│   ├── td_level.ron → TdLevelDef
│   ├── spawn_td_level → 程序化生成竞技场 + 障碍物
│   └── TdNavMesh (de_pathing 寻路)
│
└── NavMesh
    ├── AiNavMesh (vleue_navigator) — NPC 自由寻路
    └── TdNavMesh (de_pathing) — TD 敌人路径
```

## 二、两条并行管道

### 管道 A: `src/world/level.rs` — LevelPlugin

核心类型：

```rust
#[derive(States)]
enum GameLevel { None, Demo, Reception, EastWing, Courtyard, WestWing, Underground, ... }

struct ZoneDef {
    id: String,
    display_name: String,
    glb_scene: Option<String>,    // GLB 场景路径
    floor_size: f32,               // 地面大小
    floor_color: (f32, f32, f32),  // 地面颜色
    collectibles: Vec<Vec3>,
}

struct ZoneBank { zones: HashMap<String, ZoneDef> }  // 硬编码数据源
```

`load_zones()` 在 Startup 时硬编码插入 ZoneDef，当前仅 "demo" 有数据。

`spawn_narrative_zone()` 在 `OnEnter(GameLevel)` 时：
1. 始终生成 `Collider::ground(0.0)` 碰撞平面
2. 如果 ZoneDef 有 `glb_scene` → 加载 GLB
3. 如果无 GLB → 生成带纹理的 Plane3d 地面

### 管道 B: `src/world/level_tool.rs` — LevelToolPlugin

RON 数据源：`assets/level/level_config.ron`

```ron
(
    levels: {
        "Demo": (
            map: (width, height, depth, grid_unit, terrain_model, skybox, ...),
            npcs: [{ name, model_path, position, conversation_id, patrol_route, ... }],
            collectibles: [{ name, model_path, position, pickup_function, ... }],
            proximity_models: [{ id, path, position, scale, load_distance, ... }],
            sound_triggers: [{ state, sound_file, trigger_type, volume }],
            menu: Some({ title, background, buttons }),
        ),
        "EastWing": (...),
        "WestWing": (...),
        ...
    },
)
```

`spawn_level_content()` 在 `OnEnter(GameLevel)` 时（**与 A 并行**）：
1. 查询 LevelToolData 中当前关卡的 LevelDef
2. spawn_npcs → 生成 NPC + DialogueTrigger + Navigator
3. spawn_collectibles → 生成收集品
4. register_proximity_models → 注册距离加载模型
5. 清理由 level.rs 的 cleanup_level(LevelEntity) 统一处理

### 管道 C: `src/td/` — TD 子系统

独立状态，由 `GamePhase::Playing` 守卫运行。

- 关卡定义：`assets/td_level.ron`（竞技场大小、核心位置、障碍物、出生点）
- 导航网格：`TdNavMesh`（基于 de_pathing 库的 Polyanya 寻路）
- 空间网格：`TdGridResource`（手动管理 Entity 空间索引）

## 三、关卡数据流

```
编译期
  assets/level/level_config.ron
  → include_str!() → ron::de::from_str()
  → LevelToolData { config: LevelToolConfig }
  → Resource

运行时
  LoadLevelEvent { level: GameLevel }
  → handle_level_transition()
  → NextState<GameLevel>::set(new_level)
  → OnExit(old_level): cleanup_level()         → despawn all LevelEntity
  → OnEnter(new_level):
       LevelPlugin::spawn_narrative_zone()      → 地面/GLB 场景
       LevelToolPlugin::spawn_level_content()   → NPC/收集品/模型/音效

清理
  LevelEntity 标记组件 → OnExit → despawn_recursive
  ProximityModels.spawned → 单独清理
```

## 四、存在的问题

### 问题 1: 双管道数据源重复

`spawn_narrative_zone()`（管道 A）和 `spawn_level_content()`（管道 B）响应 **同一个 OnEnter 事件**，但：

| 方面 | 管道 A (level.rs) | 管道 B (level_tool.rs) |
|------|-------------------|----------------------|
| 数据源 | ZoneBank（硬编码） | level_config.ron |
| 地面信息 | floor_size, floor_color, glb_scene | MapDef 中也有 terrain_model |
| 场景模型 | GLB 场景仅 Demo 有 | level_config.ron 所有关卡都有 |
| NPC/收集品 | 无 | RON 驱动 |

同一个关卡属性（地面大小、颜色、场景模型）分散在两种数据源中，**修改一个关卡需要改两处**。

### 问题 2: ZoneBank 数据不完整

当前 ZoneBank 只有 "demo" 一个区域有数据（`load_zones()` 硬编码），其他 9 个关卡枚举无对应 ZoneDef。实际运行时其他关卡只有碰撞平面，没有地面渲染。

### 问题 3: Demo 关卡的 ProximityModel 硬编码

`spawn_all_preview_models()` 在 level.rs 中硬编码注册了 31 个 ProximityModel，而 level_config.ron 的 Demo 关卡也有 proximity_models 数组。**两者并存且不协调** — 硬编码的那些模型不在 RON 中，RON 中的模型却在运行时未被正确使用。

### 问题 4: 两套独立 NavMesh

| 系统 | 库 | 用于 | 文件 |
|------|-----|------|------|
| `AiNavMesh` | vleue_navigator (Polyanya) | NPC 自由寻路 | `src/ai/pathfinding/nav_mesh.rs` |
| `TdNavMesh` | de_pathing (Polyanya) | TD 敌人路径 | `src/world/nav_mesh.rs` |

两者本质都是 Polyanya 算法，但：

- 使用不同的库（vleue_navigator vs de_pathing）
- 依赖不同的 crate（需要同时维护两个依赖）
- 障碍物定义不互通
- TD 敌人不能复用 NPC 的 `Navigator` + `follow_nav_path` 系统

### 问题 5: LevelTool 的 MapDef 与 ZoneDef 字段重叠

```rust
// ZoneDef (level.rs)
struct ZoneDef {
    floor_size: f32,
    floor_color: (f32, f32, f32),
    glb_scene: Option<String>,
}

// MapDef (level_tool.rs)
struct MapDef {
    width: f32, height: f32, depth: f32,   // 相当于 floor_size
    terrain_model: Option<String>,          // 相当于 glb_scene
    skybox, ambient_light, fog_color, ...
}
```

`MapDef.width × height` 等价于 `ZoneDef.floor_size`，`MapDef.terrain_model` 等价于 `ZoneDef.glb_scene`。

## 五、重构方案

### 目标

1. **统一数据源**：所有关卡数据从 `level_config.ron` 读取，删除 ZoneBank 硬编码
2. **统一 OnEnter 触发**：删除 `spawn_narrative_zone()`，所有生成走 `spawn_level_content()`
3. **统一 NavMesh**：TD 改用 vleue_navigator，删除 de_pathing 依赖

### 步骤 1: MapDef 扩展地面字段

在 `level_tool.rs` 的 `MapDef` 中添加 ground 信息，替换 ZoneDef：

```rust
struct MapDef {
    // 现有字段
    width: f32,
    height: f32,
    depth: f32,
    grid_unit: f32,
    terrain_model: Option<String>,
    skybox: Option<String>,
    ambient_light: String,
    fog_color: String,
    fog_near: f32,
    fog_far: f32,

    // 新增字段（替代 ZoneDef）
    glb_scene: Option<String>,        // GLB 场景路径（有则加载，无则生成地面）
    floor_color: Option<(f32, f32, f32)>,  // 地面颜色（可选，默认深灰色）
    no_floor: Option<bool>,            // 完全不需要地面（如纯 GLB 场景）
}
```

### 步骤 2: 删除 ZoneBank + spawn_narrative_zone

改动 `src/world/level.rs`：

- 删除 `ZoneBank` 资源
- 删除 `ZoneDef` 结构体
- 删除 `load_zones()` 系统
- 删除 `spawn_narrative_zone()` 系统
- 删除 `spawn_zone()` 函数

在 `LevelPlugin::build()` 中移除所有 `OnEnter(GameLevel::Xxx)` 对 `spawn_narrative_zone` 的注册。

将地面生成逻辑 **合并到 LevelTool 的 `spawn_level_content()`** 中。

### 步骤 3: LevelTool 接管地面生成

在 `spawn_level_content()` 增加地面生成（源自原 `spawn_zone()`）：

```
spawn_level_content:
  1. 读取 MapDef
  2. 始终生成 Collider::ground(0.0)
  3. 如果有 glb_scene → 加载 GLB
  4. 否则如果有 floor_color → 生成带颜色的 Plane3d
  5. 否则 → 生成默认深灰色 Plane3d
  6. 生成 NPC / 收集品 / ProximityModel / 音效（不变）
```

### 步骤 4: 统一 RON 配置

将 ProximityModel 配置统一到 `level_config.ron`。删除 `spawn_all_preview_models()` 的硬编码，所有模型在 RON 中定义。

Demo 关卡的 RON 配置扩展为包含所有 31 个模型 + GLB 场景路径 + 地面颜色。

### 步骤 5: 统一 NavMesh

详见第七节。

### 改后架构

```
关卡系统（重构后）
├── LevelPlugin (src/world/level.rs)
│   ├── GameLevel 状态机（保留）
│   ├── cleanup_level（保留）
│   ├── 关卡切换事件处理（保留）
│   └── 删掉: ZoneBank, ZoneDef, load_zones, spawn_narrative_zone
│
├── LevelToolPlugin (src/world/level_tool.rs)
│   ├── level_config.ron → LevelToolConfig（唯一数据源）
│   ├── MapDef 增加地面字段
│   ├── spawn_level_content 接管地面生成
│   ├── NPC/收集品/ProximityModel/音效（保留）
│   └── OnEnter 只触发此一个系统
│
└── NavMesh (统一)
    ├── AiNavMesh (vleue_navigator) — NPC + TD 共用
    └── 删除: TdNavMesh, de_pathing 依赖
```

## 七、NavMesh 统一方案

### 现状

两套独立的 Polyanya NavMesh：

```
NPC 寻路: AiNavMesh (vleue_navigator)
  create_rect_navmesh(center, size) → 矩形 NavMesh（无障碍物）
  使用 Navigator + NavTarget + NavPath + follow_nav_path

TD 寻路: TdNavMesh (de_pathing)
  build(arena_size, obstacles) → 含障碍物的 NavMesh
  自定义 find_path() → Vec<Vec3>
  敌人单独实现路径跟随逻辑
```

### 方案：TD 改接 vleue_navigator

**改动 A** — 创建 TD 专用的 NavMesh 构建函数：

```rust
// src/td/nav_mesh.rs (新增)
use vleue_navigator::NavMesh;

pub fn build_td_navmesh(
    nav_meshes: &mut Assets<NavMesh>,
    arena_size: f32,
    obstacles: &[ObstacleDef],
) -> Handle<NavMesh> {
    let half = arena_size / 2.0;
    let padding = 0.8;

    // 外轮廓（顺时针）
    let edges = vec![
        Vec2::new(-half, -half),
        Vec2::new( half, -half),
        Vec2::new( half,  half),
        Vec2::new(-half,  half),
    ];

    // 障碍物轮廓
    let obstacles: Vec<Vec<Vec2>> = obstacles.iter()
        .filter_map(|obs| {
            let (px, _, pz) = obs.position;
            let (sx, _, sz) = obs.scale;
            let hx = sx / 2.0 + padding;
            let hz = sz / 2.0 + padding;
            let left = (px - hx).max(-half);
            let right = (px + hx).min(half);
            let bottom = (pz - hz).max(-half);
            let top = (pz + hz).min(half);
            if right <= left || top <= bottom { None }
            else { Some(vec![
                Vec2::new(left, bottom),
                Vec2::new(right, bottom),
                Vec2::new(right, top),
                Vec2::new(left, top),
            ])}
        })
        .collect();

    let mesh = NavMesh::from_edge_and_obstacles(edges, obstacles);
    nav_meshes.add(mesh)
}
```

**改动 B** — `AiNavMesh` 增加 TD 兼容：

```rust
// src/ai/pathfinding/nav_mesh.rs
pub struct AiNavMesh {
    pub handle: Handle<NavMesh>,
}
```

不用改 — TD 只需要传入自己的 Handle，NPC 和 TD 共享同一个 `Assets<NavMesh>`。

**改动 C** — TD 敌人改用 Navigator + follow_nav_path：

```rust
// TD Startup 时构建
fn td_build_navmesh(
    level: Res<TdLevelDef>,
    mut nav_meshes: ResMut<Assets<NavMesh>>,
    mut ai_nav: ResMut<AiNavMesh>,
) {
    ai_nav.handle = build_td_navmesh(&mut nav_meshes, level.arena_size, &level.obstacles);
}

// TD 敌人生成时（替换自定义路径跟随）
commands.spawn((
    Navigator::new(enemy.speed),
    NavTarget::new(core_pos),
    // follow_nav_path 自动处理移动
));
```

**改动 D** — 删除旧文件：

| 删除 | 文件 |
|------|------|
| `TdNavMesh` | `src/world/nav_mesh.rs` |
| de_pathing 依赖 | `Cargo.toml` |
| TD 自定义路径跟随 | `src/td/enemy.rs` 中替代为 Navigator |

### 统一后的 NavMesh 架构

```
Assets<NavMesh> (vleue_navigator)
├── NPC 寻路: create_rect_navmesh() → Handle
├── TD 寻路:   build_td_navmesh() → Handle
└── 未来:      from_edge_and_obstacles() → 任意形状

AiNavMesh { handle }  ← 当前活跃的 NavMesh Handle

系统层:
  Navigator + NavTarget + NavPath
  → detect_nav_target → compute_path (NavMesh::path) → follow_nav_path
```
