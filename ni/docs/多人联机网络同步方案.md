# 多人联机网络同步方案

> 基于现有 TCP 聊天架构，扩展为多人游戏状态同步系统

## 一、网络架构

### 当前架构（聊天系统）

```
                    ┌──────────────────┐
                    │    Host/Server   │
                    │  (TcpListener)   │
                    └────────┬─────────┘
                             │ TCP (JSON)
                    ┌───────┴────────┐
                    │                │
              ┌─────▼─────┐   ┌─────▼─────┐
              │  Client 1 │   │  Client 2 │
              └───────────┘   └───────────┘
```

- **拓扑**：监听服务器（Listen Server），Host 同时是玩家
- **传输**：TCP，长度前缀帧
- **序列化**：JSON
- **现有限制**：仅聊天文本，无游戏状态同步

### 目标架构（游戏同步）

```
                    ┌──────────────────┐
                    │  Host/Server     │
                    │  ├ 游戏循环       │
                    │  ├ 快照生成 (20Hz)│
                    │  └ 消息转发       │
                    └────────┬─────────┘
                             │ TCP (混合消息)
                    ┌───────┴────────┐
                    │                │
              ┌─────▼─────┐   ┌─────▼─────┐
              │  Client 1 │   │  Client 2 │
              │  ├ 插值平滑 │   │  ├ 插值平滑 │
              │  └ 输入采集 │   │  └ 输入采集 │
              └───────────┘   └───────────┘
```

## 二、消息协议

### 协议定义

现有的 `WireMessage` 升级为消息枚举：

```rust
/// 网络消息枚举
enum GameMessage {
    // ── 聊天（现有）──
    Chat {
        from: String,
        text: String,
    },

    // ── 快照同步（新增）──
    Snapshot {
        seq: u32,
        entities: Vec<EntityState>,
    },

    // ── 玩家输入（可选，用于权威模式）──
    PlayerInput {
        seq: u32,
        input_flags: u8,  // 位标记
    },

    // ── 系统消息 ──
    System {
        text: String,
    },
}

/// 单个实体的状态快照
struct EntityState {
    id: u32,
    pos: (f32, f32, f32),
    rot: (f32, f32, f32, f32),
    anim_state: u8,    // 当前动画状态
    health: f32,        // 血量（可选）
}
```

### 帧格式

沿用现有的长度前缀 + JSON 方案，只是消息体变为枚举：

```
┌────────────┬──────────────────────────┐
│  4 字节    │     N 字节               │
│ (大端长度)  │     JSON 字节            │
├────────────┼──────────────────────────┤
│ 0x00000032 │ {"Snapshot":{"seq":42,...}} │
└────────────┴──────────────────────────┘
```

**可选升级路径**：
- JSON → `bincode`（二进制，体积缩小 60%，解析速度提升 10x）
- 需要 enum 序列化支持，`serde` 的 `#[derive(Serialize, Deserialize)]` 直接支持 tagged enum

## 三、方案对比

### 方案 A：快照同步（Snapshot Sync）— 推荐起步

| 项目 | 说明 |
|------|------|
| **原理** | 服务端每 50ms 收集所有实体状态，广播给所有客户端 |
| **客户端处理** | 客户端收到快照后，从当前位置 Lerp 到目标位置 |
| **优点** | 实现简单，网络容忍度高（丢包只丢一帧），带宽可控 |
| **缺点** | 所有玩家感受到 50-100ms 延迟；高频动作（近战）可能不准 |
| **适用** | 探索、合作、休闲 RPG |
| **带宽** | 20 Hz × 10 实体 × ~100 bytes ≈ 20 KB/s |

### 方案 B：状态复制（State Replication）

| 项目 | 说明 |
|------|------|
| **原理** | 每个实体只在状态变化时发送更新（dirty flag），服务端转发 |
| **客户端处理** | 收到增量更新，插值到最新状态 |
| **优点** | 带宽利用率高，静止实体不产生流量 |
| **缺点** | 实现比快照复杂，需要脏标记追踪 |
| **适用** | 大量实体但多数静止的场景 |
| **带宽** | 取决于变化频率，通常只有快照的 20-50% |

### 方案 C：输入同步 / 权威服务器

| 项目 | 说明 |
|------|------|
| **原理** | 客户端只发按键输入，服务端运行完整游戏模拟，输出计算结果 |
| **客户端处理** | 客户端预测 + 服务端回滚修正（需要状态回滚框架） |
| **优点** | 防作弊，所有玩家看到一致的世界 |
| **缺点** | 实现极复杂（需要服务端模拟完整游戏逻辑、状态回滚），延迟补偿困难 |
| **适用** | 竞技 FPS、格斗、RTS |
| **带宽** | 极低（仅输入，~1 KB/s） |

### 推荐选择

**短期（原型阶段）→ 方案 A：快照同步**
- 在现有 TCP + JSON 基础上直接扩展
- 1-2 天可跑通

**中期 → 方案 B：状态复制**
- 优化带宽
- 配合 Bevy 的 Component 系统天然适配脏标记

**长期竞技需求 → 方案 C：输入同步**
- 需要服务端能跑全部游戏逻辑
- 需要帧同步框架

## 四、Bevy 组件设计

### 新增组件

```rust
/// 标记需要网络同步的实体
#[derive(Component)]
struct NetworkId(u32);

/// 标记此实体由网络控制（非本地玩家）
#[derive(Component)]
struct NetworkControlled;

/// 客户端插值缓冲：存储最近几个快照位置
#[derive(Component)]
struct InterpBuffer {
    snapshots: VecDeque<(f32, Vec3)>,  // (接收时间, 位置)
}

/// 实体拥有者标记
#[derive(Component)]
struct NetworkOwner {
    client_id: u32,
}
```

### 组件分层

```
本地玩家实体：
  Player
  Transform
  NetworkId(1)
  NetworkOwner(client_id: 0)     ← 自己拥有
  → 不上行同步位置（直接控制）

远程玩家实体：
  NetworkId(1)
  NetworkControlled
  InterpBuffer
  Transform (由插值系统每帧更新)
  NetworkOwner(client_id: 1)     ← 别人拥有
  → 只由网络系统控制位置
```

### 快照收集（服务端）

```rust
fn collect_snapshot(
    entities: Query<(&NetworkId, &Transform)>,
    mut seq: Local<u32>,
    server_state: Res<ServerState>,
) {
    *seq += 1;
    let snapshot = entities.iter().map(|(id, tf)| EntityState {
        id: id.0,
        pos: (tf.translation.x, tf.translation.y, tf.translation.z),
        rot: (tf.rotation.x, tf.rotation.y, tf.rotation.z, tf.rotation.w),
        anim_state: 0,
        health: 100.0,
    }).collect();
    server_state.broadcast(GameMessage::Snapshot {
        seq: *seq,
        entities: snapshot,
    });
}
```

## 五、客户端插值与预测

### 快照插值

```
收到 Snapshot(seq=50, pos=(10,0,5))
         │
         ▼
缓存到 InterpBuffer
         │
   每帧更新：
         │
         ▼
prev = buffer[0]  (上一个快照的插值目标)
next = buffer[1]  (最新快照位置)
t = (当前时间 - prev.time) / (next.time - prev.time)
transform.translation = prev.pos.lerp(next.pos, t.clamp(0,1))
```

### 视觉插值系统

```rust
fn interpolate_entities(
    mut entities: Query<(&mut Transform, &mut InterpBuffer)>,
    time: Res<Time>,
) {
    for (mut transform, mut buffer) in entities.iter_mut() {
        if buffer.snapshots.len() < 2 {
            return;
        }

        // 取最旧的两个快照做插值
        let s0 = buffer.snapshots[0];
        let s1 = buffer.snapshots[1];
        let elapsed = time.elapsed_secs() - s0.0;
        let duration = s1.0 - s0.0;
        let t = (elapsed / duration).clamp(0.0, 1.0);

        transform.translation = s0.1.lerp(s1.1, t);
    }
}
```

## 六、网络频率与控制

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| **快照频率** | 20 Hz (50ms) | 平衡延迟与带宽 |
| **输入发送频率** | 30-60 Hz | 输入需要更高精度 |
| **快照保留数** | 2-3 帧 | 应对网络抖动 |
| **插值延迟** | 50-100ms | 给插值预留缓冲时间 |
| **超时断线** | 5 秒无响应 | 判定客户端离线 |

## 七、网络线程架构

复用现有的 `crossbeam_channel` 通道模式：

```
                    ┌──────────────────────┐
   GameMessage      │    Network Thread    │     GameMessage
   ───────────────► │   (独立线程运行)      │ ◄───────────────
   outgoing_tx      │                      │   incoming_tx
                    │  TCP send/recv loop  │
                    └──────────────────────┘
```

新增一个通道或消息类型即可——游戏同步消息和聊天消息走同一条 TCP 连接，通过 `GameMessage` 枚举区分。

## 八、实现步骤

### Step 1：协议升级
- 将 `WireMessage` 改为 `GameMessage` 枚举
- 增加 `Snapshot` 变体
- 保持 TCP 帧格式不变

### Step 2：服务端快照广播
- 在 Host 的游戏循环中新增 `collect_snapshot` 系统
- 频率控制：20 Hz（每 3 帧一次）
- 广播给所有已连接客户端（复用现有 `clients` 列表）

### Step 3：客户端接收与插值
- 解析 `GameMessage::Snapshot`
- 找到本地对应的实体（通过 `NetworkId` 匹配）
- 写入 `InterpBuffer`
- 每帧跑插值系统

### Step 4：本地玩家输入上传
- 采集本地玩家的移动输入（WASD 等）
- 编码为 `PlayerInput` 消息
- 发送到服务端

### Step 5：冲突与延迟补偿（可选）
- 本地预测：本地玩家不等待网络确认，即时移动
- 状态对齐：收到服务端快照后修正偏差

## 九、边界情况处理

| 场景 | 处理方式 |
|------|----------|
| **客户端断线重连** | 服务端发送完整快照，客户端重建所有 NetworkControlled 实体 |
| **新玩家加入** | 服务端下发当前全量快照（state dump） |
| **高延迟玩家** | 客户端增加插值缓冲深度（3-4 帧），平滑牺牲响应速度 |
| **丢包抖动** | 如果下一帧快照未到，保持当前位置，不做跳帧 |
| **玩家离开** | 服务端广播 RemoveEntity 消息，客户端清理对应实体 |
| **NAT 穿透** | 局域网无需处理；互联网部署可用 `natpmp` 或中继服务器 |

## 十、性能参考

| 场景 | 带宽 | 客户端 CPU |
|------|------|------------|
| 2 玩家，JSON，20 Hz | ~4 KB/s | < 0.1% |
| 4 玩家，JSON，20 Hz | ~10 KB/s | < 0.2% |
| 10 玩家，JSON，20 Hz | ~25 KB/s | ~0.5% |
| 10 玩家，bincode，20 Hz | ~8 KB/s | ~0.2% |
| 10 玩家，bincode，60 Hz | ~24 KB/s | ~0.5% |

> 以上为实体数量 ≈ 20 个（玩家 + NPC + 收集品）的估算值。
> JSON 每个实体约 100 bytes，bincode 约 30 bytes。

## 十一、后续扩展方向

1. **传输层升级**：TCP → QUIC (`quinn` crate) 或 UDP + 自定义可靠性层
2. **房间系统**：多人房间创建/加入/列表，独立游戏循环
3. **同步范围裁剪**：只同步玩家附近（~50m）的实体，支持大世界
4. **权威验证**：服务端校验玩家移动速度、位置合法性
5. **语音聊天**：通过 Opus 编码 + UDP 传输
6. **Steam 集成**：使用 Steamworks SDK 处理好友邀请和 NAT 穿透
